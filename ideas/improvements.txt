 ## New `DatabaseKeyStore.kt`

 Conceptually:

```
class DatabaseKeyStore(
    private val context: Context
) {
    fun getOrCreateDatabaseKey(): ByteArray {
        val wrapped = preferences.getString(WRAPPED_KEY, null)

        return if (wrapped != null) {
            unwrap(Base64.decode(wrapped, Base64.NO_WRAP))
        } else {
            val databaseKey = ByteArray(32).also {
                SecureRandom().nextBytes(it)
            }

            val encrypted = wrap(databaseKey)

            preferences.edit()
                .putString(
                    WRAPPED_KEY,
                    Base64.encodeToString(
                        encrypted,
                        Base64.NO_WRAP
                    )
                )
                .commit()

            databaseKey
        }
    }
}
```

 The important implementation detail is:

```
private fun getWrappingKey(): SecretKey
```

 which obtains/creates an AES key inside Android Keystore.

 Then:

```
Cipher.getInstance("AES/GCM/NoPadding")
```

 is used to wrap the 32-byte SQLCipher key.

 Persist:

```
version
IV
ciphertext
authentication tag
```

 You don't need to invent a custom format. A small versioned binary envelope is sufficient:

```
[version][IV][ciphertext+tag]
```

 # 3\. Backward compatibility is critical

 This is the tricky part.

 Existing users currently have:

```
database
   +
fallback key in SharedPreferences
```

 You **cannot simply start using a new key**.

 That would make every existing database unreadable.

 Migration should therefore be:

```
existing installation
        │
        ▼
read existing fallback key
        │
        ▼
open existing SQLCipher DB
        │
        ▼
generate Keystore wrapping key
        │
        ▼
wrap existing DB key
        │
        ▼
persist wrapped key
        │
        ▼
verify DB opens using wrapped key
        │
        ▼
ONLY THEN remove legacy key
```

 This is a **key migration**, not a Room schema migration.

 That's important.

---

 ## Proposed API

```
class DatabaseKeyStore(...) {

    fun getDatabaseKey(): ByteArray {
        return readWrappedKey()
            ?: migrateLegacyKey()
            ?: createNewDatabaseKey()
    }

    private fun migrateLegacyKey(): ByteArray {
        val legacy = readLegacyFallbackKey()
            ?: return null

        val wrapped = wrap(legacy)

        persistWrappedKey(wrapped)

        // Verify before deleting legacy material.
        check(unwrap(wrapped).contentEquals(legacy))

        deleteLegacyKey()

        return legacy
    }
}
```

 Don't delete the legacy key until the new key can actually be read back.

 # 22\. Database migration

 If current DB version is `N`, make:

```
N → N+1
```

 Add:

```
ALTER TABLE captured_items
ADD COLUMN content_hash TEXT;
```

 Then populate hashes for existing rows.

 But SQLite migration cannot conveniently call your Kotlin hashing code inside a Room migration.

 So use a two-phase approach:

 ### Schema migration

```
N → N+1
```

 adds nullable:

```
content_hash
```

 ### Post-open backfill

 A `WorkManager` job computes hashes in batches.

 Once complete:

```
content_hash
```

 can become enforced for **new inserts**, while old data remains compatible.

 Don't attempt a risky destructive table rebuild just to make the column non-null.

 Room's migration model is specifically intended to preserve existing user data through incremental migrations, and migration tests should be part of the release.  Android Developers

```
     ├── same text
     ├── same metadata
     └── searchable
```

 I'd turn that into an automated assertion.

 For example:

```
data class DatabaseSnapshot(
    val count: Int,
    val ids: Set<Long>,
    val contentHashes: Set<String>
)
```

 Take snapshot before migration and after migration.

 Then assert equality.

 # 43\. One change I'd make to the original audit

 I would **not rush to Room 3** despite the fact that Room 3 is now available. Current documentation describes it as a major transition with new packages and APIs, and SQLCipher only recently added Room 3 support.  Android Developers+1

 For ActivityTrace, the safer path is:

```
Current Room 2
      ↓
fix security
      ↓
upgrade Room 2.x
      ↓
migrate SQLCipher
      ↓
stabilize
      ↓
Room 3 later
```

 That minimizes the number of moving parts in the security-critical release.

 # 44\. Recommended final architecture

 After P0/P1, the system should look like this:

```
                         ┌─────────────────────┐
                         │      Compose UI     │
                         └──────────┬──────────┘
                                    │
                              ViewModels
                                    │
                         ┌──────────▼──────────┐
                         │   SearchRepository  │
                         └──────────┬──────────┘
                                    │
                                  FTS5
                                    │
                         ┌──────────▼──────────┐
                         │  Encrypted Room DB  │
                         │      SQLCipher      │
                         └──────────▲──────────┘
                                    │
                           CaptureRepository
                                    ▲
                                    │
                         ┌──────────┴──────────┐
                         │     PrivacyFilter   │
                         └──────────▲──────────┘
                                    │
                  ┌─────────────────┼──────────────────┐
                  │                 │                  │
            Notifications      Accessibility         Files
                  │                 │                  │
                  └─────────────────┼──────────────────┘
                                    │
                              ContentHasher
                                    │
                              Deduplication
                                    │
                              Database insert

                  Android Keystore
                         │
                   AES wrapping key
                         │
                         ▼
                  wrapped DB key
                         │
                         ▼
                    SQLCipher
```

 The important security property is:

 > **Untrusted/sensitive external content passes through the privacy filter before it becomes durable application data.**

 And the important reliability property is:

 > **No database-opening failure is ever allowed to destroy user history.**

 Those two principles should become architectural invariants rather than individual fixes.

 ## The first three PRs I'd implement

 If you want to start coding immediately, I would do exactly this:

 1. **`security/keystore-db-key`** — fix the encryption/key hierarchy and migrate existing fallback keys.
2. **`security/no-destructive-db-recovery`** — eliminate database deletion and add recovery-state handling.
3. **`privacy/accessibility-filter`** — introduce `PrivacyFilter`, password/editable-field rejection, sensitive-app policies, and bounded tree traversal.

 Those three changes address the highest-risk failure modes without touching search or the SQLCipher dependency, giving you a clean, testable security baseline before the larger P1 work.  Android Developers+1
